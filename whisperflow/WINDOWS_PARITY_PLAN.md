# Windows Parity Plan — Verbal Desktop

Handoff for the Claude Code session running **on a Windows machine**. Goal, architecture, what's
already done, and the remaining native workstreams (W3–W9). Read this first, then the per-workstream
spec in `windows_specs/`.

---

## 1. The goal

**Pixel + feature parity between the Windows desktop app and the macOS desktop app.**

The macOS app (`app/main.py`, a `rumps` menubar app) hosts every UI surface in a **WKWebView** whose
HTML is generated by `app/*_html.py`. The Windows app (`app/win_main.py`, a `pystray` tray app) hosts
the **same HTML** in **pywebview / WebView2** windows. Both talk to the **same backend**
(`app/shared_dashboard.py::DashboardApi`) over the **same JS bridge contract**. Parity means:

- Every Flume surface (dashboard, popover, overlay, meeting window, meeting HUD, autolearn widget)
  renders the identical HTML and looks the same on Windows as on Mac (see `windows_specs/W9-visual-qa.md`).
- Every feature works: dictation, sync, canvas, notes, dictionary/snippets, **meetings**,
  **autolearn**, **@-file-tags** — the last three depend on macOS-native frameworks and must be
  re-implemented with Windows equivalents.

**Rule #1 (non-negotiable):** peripheral features must **fail closed** and can NEVER break the core
`record → transcribe → inject` path. Every new native entry point is wrapped in try/except and
degrades to a no-op (or `{"ok": False, "error": ...}`) on failure.

## 2. The key architectural insight — one backend, one bridge contract

Both platforms share `DashboardApi` (in `app/shared_dashboard.py`) and the **same event contract**:

- **JS → Python (calls):** the web UI calls `window.pywebview.api.<method>(...args)` and gets a
  Promise back. `<method>` is a method on `DashboardApi` (e.g. `get_state`, `toggle_recording`,
  `start_meeting`, `save_settings`).
- **Python → JS (events):** Python pushes `window.VerbalNative(event, payload)` — the shared event
  names (`recordingState`, `state`, `result`, `devices`, `selectTab`, `canvasRemote`,
  `meetingsUpdated`, …).

### Where the two platforms differ — and why it doesn't matter to the UI

| | macOS | Windows |
|---|---|---|
| Host | WKWebView in an `NSWindow`/`NSPanel` | pywebview window (WebView2 / EdgeChromium) |
| `window.pywebview.api` | **faked** by a JS `_SHIM` (see below) | **native** — pywebview injects it for real |
| Event push | `webview.evaluateJavaScript_completionHandler_(js)` | `window.evaluate_js(js)` |

On **macOS**, `app/flume_web_dashboard.py` injects a `_SHIM` user-script at document-start that makes
WKWebView *look like* pywebview:

```js
// app/flume_web_dashboard.py::_SHIM  (macOS only)
window.pywebview = { api: new Proxy({}, { get: function(_, name){
  return function(){ ... postMessage({id, method:name, args}) ... return Promise; };
}})};
window.__flumeResolve = function(id, jsonStr){ ... resolve the promise ... };
```

On **Windows under real pywebview** there is **no shim** — `window.pywebview.api` is the genuine
bridge to the Python `js_api` object (`DashboardApi`) passed to `webview.create_window(...)`.

### The HTML is already dual-target

`app/flume_dashboard_html.py::flume_html()` is written so the **same string** works on both hosts:

- It defines a **safe `api()` wrapper** that never throws before the bridge exists:
  ```js
  // flume_dashboard_html.py ~line 479
  function api(name){ const a=[].slice.call(arguments,1);
    return (window.pywebview && window.pywebview.api && window.pywebview.api[name])
      ? window.pywebview.api[name].apply(null,a) : Promise.resolve({ok:false}); }
  ```
- It **waits for the bridge** before loading state:
  ```js
  window.addEventListener('pywebviewready', load);   // flume_dashboard_html.py ~line 1712
  ```
  `pywebviewready` fires natively under pywebview; on macOS the `_SHIM` installs `window.pywebview`
  at document-start so the guard passes there too.
- It receives native events via `window.VerbalNative = function(event, payload){ ... }` (~line 1612).

**Implication for you:** you almost never touch the HTML. When you wire a new surface on Windows you
render the existing `*_html.py` string into a pywebview window and pass a `js_api` object (a
`DashboardApi`, or a small surface-specific bridge that mirrors the Mac panel's bridge methods).

## 3. What's already done (Mac side + shared)

- **Dashboard renders `flume_html()` on Windows.** `app/shared_dashboard.py::SharedDashboard.show()`
  already calls `webview.create_window("Flume", html=flume_html(), js_api=DashboardApi(self),
  width=980, height=680, min_size=(760,520), background_color="#0e1012")` then `webview.start()`.
  This is the parity anchor — the retired light-theme `app/win_dashboard.py::WinDashboard` is only a
  last-resort fallback if `import webview` fails.
- **`DashboardApi` is the single shared backend** for both platforms (state, history, canvas, notes,
  dictionary, snippets, settings, sync, pairing, and the meeting method surface).
- **Dictation pipeline** works on Windows today (`app/win_main.py`: hotkey → `Recorder` →
  `transcribe` → `process_text` → `win_injector.inject_text`). Overlay/toast/build wiring is in
  progress and finalized by the workstreams below.
- **Fonts** are handled cross-platform via `app/fonts_css.py::web_font_css()` (base64 `@font-face`).
  `app/theme.py` is **macOS-only** (imports AppKit) and is deliberately NOT bundled on Windows — the
  web UIs use `fonts_css.py`.
- **`verbal-win.spec` and `requirements-win.txt` are pre-wired** for the native modules you'll create:
  `app.win_system_audio`, `app.win_editwatch`, `app.win_ax` are already in `hiddenimports`, and
  `uiautomation`, `comtypes`, `soundcard`, `winotify` are already in `requirements-win.txt`. You add
  the module files; the build already expects them.

## 5. The Mac ↔ Windows module-pairing convention

Native platform code lives in **paired modules** that expose the **same public interface**, so the
cross-platform callers (`shared_dashboard.py`, `meetings.py`, and the pipeline) don't branch on OS —
they import the platform module and call the shared method names.

| macOS module | Windows module | Shared public interface (what callers rely on) |
|---|---|---|
| `app/injector.py` | `app/win_injector.py` | `save_focused_app()`, `get_focused_app_name()`, `get_focused_app_pid()`, `get_focused_app_bundle()`, `restore_focused_app()`, `inject_text(text, allow_mentions=False)` |
| `app/overlay.py` (`OverlayBar`) | `app/win_overlay.py` (`WinOverlay`) | `setup()`, `show(status)`, `update_status(status)`, `show_briefly(status, duration)`, `hide()`, `visible` |
| `app/system_audio.py` | `app/win_system_audio.py` *(new)* | `is_supported()`, `run_capture_test(app, seconds)`, `SystemAudioCapture(on_audio)` with `.start()/.stop()/.level/.error/.running` |
| `app/autolearn.py` (`EditWatcher`) | `app/win_editwatch.py` *(new)* | `EditWatcher().arm(pid, bundle, inserted_text, on_decision_callback)`, `.cancel()` — **reuse** the portable `classify()`/`align()`/guard core from `autolearn.py` |
| `app/filetags.py` | `app/win_ax.py` *(new)* | `read_open_files(pid, ...)`, `supported_ide(...)`, `harvest_async(...)`, `focus_is_terminal()` — **reuse** the pure rewrite/prompt logic from `filetags.py` |
| `app/permissions.py` (macOS) | `app/permissions.py` Windows branch *(new)* | `all_status()`, `meeting_permissions()`, `check_*`/`request_*`, `system_audio_capture_supported()` |

Rendering surfaces are NOT paired modules — the **HTML is shared** (`overlay_html.py`,
`flume_popover_html.py`, `meeting_html.py`, `meeting_hud_html.py`, `autolearn_widget.py::autolearn_widget_html()`).
Only the **host container** differs: macOS uses `NSPanel`+WKWebView classes; Windows uses pywebview
windows. On Windows you host these with small window wrappers (see each spec) that render the shared
HTML and expose a `js_api` bridge with the same method names the Mac panel's `_dispatch` handles.

**Guiding rule:** if you find yourself editing a shared `*_html.py`, stop — parity means the Windows
container adapts to the HTML, not the reverse. The only shared-file edits allowed are in
`shared_dashboard.py`/`permissions.py`/`meetings.py` *behind a platform check* to activate a method
that currently returns `"unavailable"` on Windows.

## 6. Build / run / test on Windows

### Dependencies

```
pip install -r requirements-win.txt
```

Already includes: `pywebview==5.3`, `pystray`, `pynput`, `sounddevice`, `soundcard` (WASAPI loopback
fallback), `winotify` (native toasts), and `uiautomation==2.0.20` + `comtypes==1.4.6` (the AX
equivalent for W7/W8). WebView2 runtime must be present on the machine (ship the Evergreen bootstrapper
with the installer if targeting clean machines).

### Run from source

```
python -m app.win_main
```

### Build the frozen exe

```
pyinstaller verbal-win.spec        # or: bash build-win.sh
```

`verbal-win.spec` already lists the new native modules in `hiddenimports`
(`app.win_system_audio`, `app.win_editwatch`, `app.win_ax`) and their libs (`uiautomation`,
`comtypes`, `comtypes.client`). Fonts are bundled to `app/assets/fonts` so `fonts_css.py` resolves
them from `sys._MEIPASS`. **Do NOT add `app.theme` to the spec** — it imports AppKit and will break
the frozen Windows exe (comment in the spec says so).

### Human smoke-test checklist (run after each workstream)

1. **Dictation:** hotkey (Right Alt) → speak → text pastes into the focused app. Overlay shows
   Recording → Transcribing → Done. Sound cues play (`winsound`).
2. **Overlay (W3):** pill is always-on-top, does NOT steal focus (you can keep typing in the target),
   fades in/out, buttons (stop/cancel/pause/copy) work.
3. **Popover (W4):** tray left-click opens the compact popover; record/sync toggle/history/canvas work.
4. **Dashboard:** tray → Open Verbal → full Flume UI; tabs, history, notes, canvas, settings, sync.
5. **Injection + file-tags (W5/W8):** dictate into Cursor/VS Code with file-tagging on → `@name.ext`
   becomes a real mention chip.
6. **Meetings (W6):** Start meeting → system-audio + mic captured → live transcript → summary saved.
   Run the 3-second "Test capture" self-test.
7. **Autolearn (W7):** dictate a word, correct it in the target field → confirm pill offers to learn.
8. **Visual QA (W9):** diff each surface against the Mac screenshots.
9. **Fail-closed check:** disable/deny each native capability and confirm dictation still works.
